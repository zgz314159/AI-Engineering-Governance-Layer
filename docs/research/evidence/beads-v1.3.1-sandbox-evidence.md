## 4. `BEADS_DIR` external store, non-git cwd

```
export BEADS_DIR=/tmp/aegl-beads-research/sandbox/external/beads   # parent existed
cd <non-git dir>; bd init --stealth -q          # wall time 5.29 s
cwd BEFORE: empty     cwd AFTER: empty          # cwd fully untouched; no git init
```

`BEADS_DIR` is the `.beads` directory itself. Layout inside it:

```
config.yaml  .gitignore  .local_version  metadata.json  README.md
embeddeddolt/<name>/        dolt.gate.lock   embeddeddolt.gate.lock
```

`dolt_database` was **`nogit`** — derived from the *cwd basename*, not the
`BEADS_DIR` basename. Write commands in a non-git cwd emit a harmless warning:
`warning: beads.role not configured (GH#2950)`.

### Negative result that shapes the AEGL design

Pointing `BEADS_DIR` at `<repo>/.aegl/beads` when `<repo>/.aegl/` did **not**
exist fails:

```
Error: bd init refuses to run over live bd activity on this workspace:
workspacegate: gate parent <repo>/.aegl/ must exist: lstat <repo>/.aegl: no such file or directory
```

The workspace gate file is `<BEADS_DIR>.gate.lock` (a sibling of the DB dir), so
**the parent directory of `BEADS_DIR` must exist before `bd init`.** AEGL must
`mkdir -p .aegl` (or `.aegl/beads`) first.

## 6. Dependency chain A -> B -> C (in the BEADS_DIR store)

```
A=nogit-cq4  B=nogit-vux  C=nogit-e1a
bd dep add B A   ->  ✓ B depends on A (blocks)
bd dep add C B   ->  ✓ C depends on B (blocks)

bd ready (before):   1 issue -> A only           (0.421 s)
bd ready --json:     [ {A, status open, is_blocked null} ]
bd ready --explain:  Ready(1): A "no blocking dependencies / Unblocks 1 issue(s)"
                     Blocked(2): C <- blocked by B[open];  B <- blocked by A[open]

bd update A --claim  ->  ✓ updated A
bd ready (after A claim): (none — A in_progress excluded, B/C blocked)
bd close A -r "..."  ->  ✓ closed A
bd ready (after A close): [ {B, status open} ]
bd close B -r done   ->  ✓ closed B
bd ready (after B close): [ {C, status open} ]
```

Ready-queue semantics confirmed: blocked work is withheld, and closing a task
releases exactly its dependents.

## 7. Atomic claim / conflict

```
bd --actor alice update D --claim   ->  ✓ updated D
bd --actor bob   update D --claim   ->  Error updating D: issue already claimed by alice
                                        Error: 1 of 1 issues failed to update
bd show D --json                    ->  status in_progress, assignee alice
```

Claim is assignee+status in one guarded write; a second actor is refused.

## 8. `bd prime` structure and size (3 memories, 4 issues)

```
bytes=5445  lines=121  words=826          # full CLI mode ≈ 1.1-1.4k tokens
prime --memories-only: bytes=625 lines=16
prime --hook-json: {"hookSpecificOutput":{"hookEventName":"SessionStart",
                    "additionalContext":"[bd prime] If this output is truncated ..."}}

section headers (full mode, in order):
  # Beads Workflow Context
  ## Persistent Memories (N)          <- only if memories exist; near the top
  # 🚨 SESSION CLOSE PROTOCOL 🚨
  ## Core Rules
  ## Essential Commands  (Finding Work / Creating & Updating / Dependencies & Blocking
                         / Sync & Collaboration / Project Health / Quality Tools
                         / Lifecycle & Hygiene / Structured Workflows)
  ## Common Workflows    (Starting work / Completing work / Creating dependent work)
```

**`bd prime` performs no issue queries.** It emits static workflow text plus the
persistent-memory list. It does **not** print ready / in-progress / blocked work.
With no workspace it exits 0 and prints nothing.

Because no remote was configured, nothing left the machine. Cross-machine sync

auto-adopts a git origin without consent.

## 11. Memory commands (empirical)

```
bd remember "<content>" [--key k]   ->  Remembered [k]: ...   (~0.27-0.29 s)
bd memories [search]                ->  alphabetical key/value listing
bd export --all                     ->  {"_type":"memory","key":..,"value":..}
```

Memories are plain key→value strings with no timestamp/scope/priority/TTL.
`bd prime` emits them alphabetically, near the top, capped only by
`--max-memories` / `--max-memory-chars`.
